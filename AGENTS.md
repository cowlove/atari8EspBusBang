# Repository Guidance

## Firmware Smoke Tests

- Prefer `tools/boot.sh` for routine hardware build/flash/boot tests rather than invoking `idf.py flash` directly. It records timestamped serial output under `stash/` along with the Git version and a working-tree diff, providing a useful history of boot behavior.
- If the project-root IDF build cache is stale or points at an unavailable toolchain/source path, run `idf.py fullclean` from the project root, then continue with `tools/boot.sh`. `fullclean` removes generated build state only; it leaves source files and boot logs intact.
- This reproducible history is worth the inconvenience that `boot.sh` may leave serial-monitor processes running. After each run, check for stale monitors and terminate them before starting another capture.
- The script snapshots `git diff HEAD` and `git describe`, so the diff includes both staged and unstaged changes to tracked files. Untracked file contents are not included; account for those separately when they matter to a capture.
- `boot.sh -sc` updates and boots main through the Sidecar (`tools/boot_sidecar.sh`): it builds main, builds and flashes the Sidecar app plus its spiffs with main's images staged (on `SIDECAR_PORT`), sends the Sidecar console's `reset`, then runs `cat_until` on the Sidecar's console. At main's boot report (BootStatus) the Sidecar compares main's app token (the ELF SHA-256's first 4 bytes, `appVersion`) with the staged `app.bin.gz`'s, and if they differ has main install it by OTA over the link (FetchFirmware; app only, needs `ota_1`). Builds carry no compile time (`CONFIG_APP_COMPILE_TIME_DATE` off), so an unchanged main isn't reflashed; `-DBOOT_TOKEN=<n>` (main prints `BOOT_TOKEN n`) forces a new image, for soaks of repeated updates. main's output, DONE included, reaches the Sidecar's console over the link, so main must be built with `CONFIG_A8BB_SIDECAR_ENABLE` (`CONFIG_A8BB_LOG_VIA_SIDECAR`). Exit 3 if main never runs the staged app, 5 if what it runs isn't this build. main's own SPIFFS, bootloader and partition table, the eFuse check and the crash bundle are skipped in this mode.
- **The Sidecar app can't serial-flash main.** Serial flashing is the separate `sidecar_serial_flasher/` app (flashed by hand onto the Sidecar's ESP32, then the Sidecar app flashed back): a manual step for initializing new boards, with the main board disconnected from the Atari, like an ESP-Prog. No script builds or flashes it. Staging a new `app.bin.gz` in the Sidecar's spiffs is the deliberate act that updates main, by OTA. The Sidecar app's console `reset` is a plain EN reset, unchecked (it works with an Atari attached).
- **Crashes in `-sc`:** main's panic text only reaches main's own console, so the Sidecar learns of a crash from main's next boot report (a core dump it hasn't stored). It puts main in diagnostic mode, fetches the core into its spiffs, gzipped on the fly by a writer task (`/spiffs/core/main-<token>.core.gz`; "already fetched" = a stored file named with main's `coreVersion`, no other state), has main erase its copy (EraseCore; see the TODO on losing a core) and prints `COREFILE_AVAILABLE main <path> <bytes> <token>` then `DONE`. `tools/crash_bundle.sh --sidecar` then dumps the Sidecar's spiffs with esptool, pulls the core out (`tools/spiffs_extract.py`), gunzips it and decodes it against main's ELF. A `Backtrace:` on the Sidecar's console is the Sidecar's own crash: its own coredump partition (`sidecar/partitions.csv`), decoded against `sidecar/build/sidecar.elf`. Every bundle carries both apps' builds. Limits: a crash that never reboots main (a core 1 fault stops core 0) sends no boot report; that run ends at the `RUN_SEC+600` timeout.
- `-DTEST_PANIC=<n>`: main's core 0 crashes (a wild store, hot) once `elapsedSec` passes n, once per boot that didn't follow a panic: for testing the core dump path, e.g. `boot.sh -sc -t 30 -DTEST_PANIC=20`.
- `boot.sh` refuses `-DFAKE_CLOCK` and `-DFAKE_SIO` builds (and `-qq` when the cached build has them) on any machine whose `tools/config` sets `MQTT_HOST` and `TAS`, i.e. one where it powers on a real Atari. Both are bench-only: FAKE_CLOCK drives the clock, R/W and A0, and FAKE_SIO's bank ops rewrite the bus pins' pulls and R/W's routing from core 0 while core 1 is hot (`main/fakeSio.cpp`).

## ROM core 1 boot DRAM

`startCpu1()` boots core 1 through the ROM, in DRAM that single-core IDF otherwise recycles into the heap. `main/main.cpp` reserves 0x3fceb710–0x3fceee34 (`rom_app_cpu_boot`) and, once core 1 reaches `app_cpu_main()`, returns all of it except `.data_xtos` (0x3fcedf60–0x3fcee378) to the heap: 13,068 of 14,116 bytes. This depends on how the ROM and IDF handle core 1 today, so treat it as fragile:

- **What it relies on** (measured 2026-11-06 with ESP-IDF 6.1, ESP32-S3 rev 0.2):
  - The ROM's core 1 boot writes only `_Pri_4/_Pri_5_HandlerAddress` (0x3fcee370..0x3fcee378, inside `.data_xtos`). On a cold boot and after a panic reboot, nothing else in the span changes, then or later.
  - Core 1 keeps the ROM's vectors. Faults dispatch through `.data_xtos` (`xtos_exc_handler_table` etc.), which is why it stays reserved. With it intact, a core 1 fault prints `Guru Meditation Error: Core 1 panic'ed` with the faulting PC, and core 0 then stops (no reboot), whether or not the rest is reclaimed. With those tables overwritten, the result depends on the garbage: either a core 0 "Cache error" panic or a silent core 1 death.
  - `startCpu1()` runs once per boot, and the panic hook stops core 1 instead of restarting it, so the ROM never boots core 1 again over the heap.
- **Boot-time guard:** before `startCpu1()`, the reclaimable parts are filled with 0xa5. They are reclaimed only if the pattern survives core 1's boot. Otherwise the boot prints `ROM DRAM reclaim: ... keeping the span reserved` with the changed spans. The normal boot line is `Reclaimed 13068 bytes of ROM core 1 boot DRAM`. The guard cannot see a change that makes core 1 depend on the reclaimed DRAM after boot, so rerun the probes below after any IDF, ROM-ELF or chip-revision change, or any change to `startCpu1()`, `app_cpu_init()` or the panic hook.
- **Re-verification** on the isolated bench board, with `PORT=<by-id> ./tools/boot.sh -t 40 -DFAKE_CLOCK=1 -DBOOT_CONFIG=\"BENCH\" -DROM_BOOT_PROBE=N`. Afterwards, `cmake -U ROM_BOOT_PROBE build` clears the cached define.
  - `1`: what core 1's boot changes in `.data_xtos` (snapshot diff; expect 0 bytes, because the ROM rewrites the same values) and in the reclaimed parts (expect 0), and again 3 s later. Then an 8 KB allocation should land in the reclaimed part, and the heap integrity check should pass.
  - `2`: `1`, then one `abort()`. Expect a core dump and a panic reboot, the same results again after the reboot, and DONE.
  - `3`: `1`, then a core 1 store to address 4, 5 s after core 1 starts. Expect the core 1 Guru report with PC in `app_cpu_main`. The run does not reach DONE (core 0 stops), so cap it with `timeout`, and kill any leftover `cat_until`/`cat` readers.
  - `4`: `3` without the reclaim, as the control. Its output should match `3`.
  - If the ROM layout looks different, check it: `xtensa-esp32s3-elf-objdump -h ~/.espressif/tools/esp-rom-elfs/*/esp32s3_rev0_rom.elf` (`.stack_app`, `.bss_ets` … `.bss_xtos`, `.data_xtos`) and `nm -n` for `xtos_exc_handler_table`.
- **If the guard fires or a probe disagrees:** stop reclaiming, either by dropping the `reclaimRomAppCpuBootDram()` call or by leaving the reservation alone, then re-measure. A sturdier alternative not yet tried: boot core 1 from an early `ESP_SYSTEM_INIT_FN`, before IDF recycles the ROM DRAM, and park it in an IRAM spin loop on a static stack until `setup()` releases it.

## bmon: core 0 must keep up

Core 1 pushes every bus cycle into the bmon ring (512 entries, ~0.3 ms of bus) and never waits. The bmon loop, `core0_onBmonChange()` and `core0_utilityTasks()`, must keep up and drop nothing, except inside `handlePbiRequest()`, where entries may be lost and the backlog is discarded on return. That exception is safe only because the 6502 is then in our PBI driver with interrupts masked, so it makes no write core 0 must act on, in particular the `$D1FF`/`$D301` writes that assert halt_ (only `resume6502()` releases it; a lost one hangs the 6502). New core 0 work that can run for more than a few hundred bus cycles outside a request, or a new reason for the 6502 to write those registers during one, breaks it. Full statement at `bmonArray` in `main/bmon.h`. csim's bus-cycle mode has to run bus cycles wherever the hardware does, or `resume6502()`'s 15-tick release can miss (fixed 2026-11-16 in atari800's `CPU_CSIM_Tick()`).

- **A fetched core can be lost (bookmarked 2026-11-14).** After the Sidecar fetches, verifies and stores main's core (`/spiffs/core/main-<token>.core.gz`), it has main erase it (EraseCore, diagnostic mode), so main's next boot report shows none. From then on the Sidecar's spiffs holds the only copy, until `boot.sh -sc`'s `crash_bundle.sh --sidecar` has dumped that spiffs, pulled the core out and bundled it. If that fails (esptool, the extractor, tar), or the next `-sc` run restages the spiffs first, the core is gone. Being thought about: detecting a stale core file without erasing main's. The likely fix, stateless: `-sc` packs the previous `core/main-<token>.core.gz` back into the new spiffs image, so the Sidecar sees it (its name carries main's `coreVersion`) and doesn't refetch; the last core then stays in the spiffs until the next crash overwrites it, and main's copy needn't be erased.

Idea: build cart banks and ext mem SRAM banks from smaller pieces, as base RAM already is (`mmuAllocAddBaseRam()`: up to 4 KB pieces, halving until one fits), so they can use heap dregs. Notes from the discussion:
  - The benefit is mostly using memory a contiguous allocation can't: the internal heap is several regions that never merge (main DRAM, the reclaimed 13 KB ROM core 1 span, the 16 KB IDF returns from the data cache, the DIRAM freed from IRAM), so a 16 KB ext bank can't use any region or region tail under 16 KB. Measure first: `heap_caps_print_heap_info(MALLOC_CAP_INTERNAL)` after setup on a pool machine (free and largest block per region).
  - The last allocator at boot gets most of it: today base RAM, then cart, then the ext banks (AUTO fills the SRAM budget down to `autoMinFreeSram`), so chunk the ext banks. Carts: try the whole 8/16 KB bank, fall back to halving pieces (free in the common case). A cart change is no reason for it: it reboots the Atari, and the intended path (once the Sidecar can hold the 6502's reset line low) is to hold reset while the Sidecar reboots main, so the new cart is allocated into a fresh heap. Today's cart change works partly by luck: the Atari clears its RAM after the reset, but main's state (page mappings, bank allocations, the MMU tables) carries over.
  - Evidence (user): AUTO's 16 KB SRAM bank allocations sometimes fail with well over 32 KB reported free. `autoMemConfig()` (pbi.cpp) sizes the budget from `heap_caps_get_free_size()` and then backs off a bank at a time until `extMem.init()` succeeds, so it costs a bank rather than failing; chunked banks would win that bank back in many cases. A likely source of the holes: just before, it frees the base RAM the probe didn't need (`mmuFreeUnmapBaseRam()`), which was allocated in pieces of up to 4 KB, leaving holes no 16 KB bank can use.
  - Cart banks are easy: only `cartridge.cpp`'s per-page `L1Block.pages[]` fill and `close()` touch `image[].mem` (plus a debug label in `mmu.cpp`). Ext banks: `ExtBankPool` swaps one pointer per bank (`getBank()`); chunked, a bank is an array of fixed-size chunks (say 4 KB) swapped and copied chunk by chunk, `isSRAM()` on chunk 0, and the `$4000` mapping per chunk. Also: `ExtBankPool::memcpy` copies a byte at a time; a word copy speeds every eviction.
  - Core 1 hot data: smaller pieces land in more SRAM banks; `reportHotDataBanks()` checks every cart page at boot, and the allocator could skip pieces in banks core 0 hammers.
  - Scatter/gather SIO (done as described; was: needed once ext-bank SRAM is discontiguous; base RAM pieces already push a transfer across a piece boundary onto the copy path): `mmuCheckRangeMapped()`/`mappedElseCopyIn()` return the pointer and the length of the contiguous mapped run at `addr` instead of failing; the caller walks the transfer piece by piece through a staging buffer, and at the first unmapped page requests COPYIN (COPYOUT for reads to the 6502) for the whole remainder. The 6502's copy loop reads its own address space, so mapped pages inside the remainder come back right, and the remainder always fits the PBI ROM copy buffer, so one COPYIN round finishes the command with no extra state in `handlePbiRequest()` (the user's design).
