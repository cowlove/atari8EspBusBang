# Repository Guidance

## Firmware Smoke Tests

- Prefer `tools/boot.sh` for routine hardware build/flash/boot tests rather than invoking `idf.py flash` directly. It records timestamped serial output under `stash/` along with the Git version and a working-tree diff, providing a useful history of boot behavior.
- If the project-root IDF build cache is stale or points at an unavailable toolchain/source path, run `idf.py fullclean` from the project root, then continue with `tools/boot.sh`. `fullclean` removes generated build state only; it leaves source files and boot logs intact.
- This reproducible history is worth the inconvenience that `boot.sh` may leave serial-monitor processes running. After each run, check for stale monitors and terminate them before starting another capture.
- The script snapshots `git diff HEAD` and `git describe`, so the diff includes both staged and unstaged changes to tracked files. Untracked file contents are not included; account for those separately when they matter to a capture.
- `boot.sh -sc` updates and boots main through the Sidecar (`tools/boot_sidecar.sh`): it builds main, builds and flashes the Sidecar app plus its spiffs with main's images staged (on `SIDECAR_PORT`), sends the Sidecar console's `reset`, then runs `cat_until` on the Sidecar's console. At main's boot report (BootStatus) the Sidecar compares main's app token (the ELF SHA-256's first 4 bytes, `appVersion`) with the staged `app.bin`'s, and if they differ has main install it by OTA over the link (FetchFirmware; app only, needs `ota_1`). Builds carry no compile time (`CONFIG_APP_COMPILE_TIME_DATE` off), so an unchanged main isn't reflashed; `-DBOOT_TOKEN=<n>` (main prints `BOOT_TOKEN n`) forces a new image, for soaks of repeated updates. main's output, DONE included, reaches the Sidecar's console over the link, so main must be built with `CONFIG_A8BB_SIDECAR_ENABLE` (`CONFIG_A8BB_LOG_VIA_SIDECAR`). Exit 3 if main never runs the staged app, 5 if what it runs isn't this build. main's own SPIFFS, bootloader and partition table, the eFuse check and the crash bundle are skipped in this mode.
- **The Sidecar app can't serial-flash main.** Serial flashing is the separate `sidecar_serial_flasher/` app (flashed by hand onto the Sidecar's ESP32, then the Sidecar app flashed back): a manual step for initializing new boards, with the main board disconnected from the Atari, like an ESP-Prog. No script builds or flashes it. Staging a new `app.bin` in the Sidecar's spiffs is the deliberate act that updates main, by OTA. The Sidecar app's console `reset` is a plain EN reset, unchecked (it works with an Atari attached).
- **Crashes in `-sc`:** main's panic text only reaches main's own console, so the Sidecar learns of a crash from main's next boot report (a core dump it hasn't stored). It puts main in diagnostic mode, fetches the core into its spiffs (`/spiffs/core/main.core`; "already fetched" = the stored file's SHA token matches main's `coreVersion`, no other state), has main erase its copy (EraseCore; see the TODO on losing a core) and prints `COREFILE_AVAILABLE main <path> <bytes> <token>` then `DONE`. `tools/crash_bundle.sh --sidecar` then dumps the Sidecar's spiffs with esptool, pulls the core out (`tools/spiffs_extract.py`) and decodes it against main's ELF. A `Backtrace:` on the Sidecar's console is the Sidecar's own crash: its own coredump partition (`sidecar/partitions.csv`), decoded against `sidecar/build/sidecar.elf`. Every bundle carries both apps' builds. Limits: a crash that never reboots main (a core 1 fault stops core 0) sends no boot report; that run ends at the `RUN_SEC+600` timeout.
- `-DTEST_PANIC=<n>`: main's core 0 crashes (a wild store, hot) once `elapsedSec` passes n, once per boot that didn't follow a panic: for testing the core dump path, e.g. `boot.sh -sc -t 30 -DTEST_PANIC=20`.
- `boot.sh` refuses `-DFAKE_CLOCK` and `-DFAKE_SIO` builds (and `-qq` when the cached build has them) on any machine whose `tools/config` sets `MQTT_HOST` and `TAS`, i.e. one where it powers on a real Atari. Both are bench-only: FAKE_CLOCK drives the clock, R/W and A0, and FAKE_SIO's bank ops rewrite the bus pins' pulls and R/W's routing from core 0 while core 1 is hot (`main/fakeSio.cpp`).

## Hardware Test Pool

- We maintain test hardware on `miner6.local`, with working directories `~/src/atari8EspBusBang.N` where `N` is currently `1` through `6`.
- Shorthand such as “git push and fast forward miner6 machine 3” means push the current branch, then SSH to `miner6.local` and run `git pull` in `~/src/atari8EspBusBang.3`. Apply the same mapping to similar machine-number references.

## ROM core 1 boot DRAM

`startCpu1()` boots core 1 through the ROM, in DRAM that single-core IDF otherwise recycles into the heap. `main/main.cpp` reserves 0x3fceb710–0x3fceee34 (`rom_app_cpu_boot`) and, once core 1 reaches `app_cpu_main()`, returns all of it except `.data_xtos` (0x3fcedf60–0x3fcee378) to the heap: 13,068 of 14,116 bytes. This depends on how the ROM and IDF handle core 1 today, so treat it as fragile:

- **What it relies on** (measured 2026-11-06 with ESP-IDF 6.1, ESP32-S3 rev 0.2):
  - The ROM's core 1 boot writes only `_Pri_4/_Pri_5_HandlerAddress` (0x3fcee370..0x3fcee378, inside `.data_xtos`). On a cold boot and after a panic reboot, nothing else in the span changes, then or later.
  - Core 1 keeps the ROM's vectors. Faults dispatch through `.data_xtos` (`xtos_exc_handler_table` etc.), which is why it stays reserved. With it intact, a core 1 fault prints `Guru Meditation Error: Core 1 panic'ed` with the faulting PC, and core 0 then stops (no reboot), whether or not the rest is reclaimed. With those tables overwritten, the result depends on the garbage: either a core 0 "Cache error" panic or a silent core 1 death.
  - `startCpu1()` runs once per boot, and the panic hook stops core 1 instead of restarting it, so the ROM never boots core 1 again over the heap.
- **Boot-time guard:** before `startCpu1()`, the reclaimable parts are filled with 0xa5. They are reclaimed only if the pattern survives core 1's boot. Otherwise the boot prints `ROM DRAM reclaim: ... keeping the span reserved` with the changed spans. The normal boot line is `Reclaimed 13068 bytes of ROM core 1 boot DRAM`. The guard cannot see a change that makes core 1 depend on the reclaimed DRAM after boot, so rerun the probes below after any IDF, ROM-ELF or chip-revision change, or any change to `startCpu1()`, `app_cpu_init()` or the panic hook.
- **Re-verification** on the isolated bench board, with `PORT=<by-id> ./tools/boot.sh -t 40 -DFAKE_CLOCK=1 -DBOOT_CONFIG=\"BENCH\" -DROM_BOOT_PROBE=N`. Afterwards, `cmake -U ROM_BOOT_PROBE build` clears the cached define.
  - `1`: what core 1's boot changes in `.data_xtos` (snapshot diff; expect 0 bytes, because the ROM rewrites the same values) and in the reclaimed parts (expect 0), and again 3 s later. Then an 8 KB allocation should land in the reclaimed part, and the heap integrity check should pass.
  - `2`: `1`, then one `abort()`. Expect a core dump and a panic reboot, the same results again after the reboot, and DONE.
  - `3`: `1`, then a core 1 store to address 4, 5 s after core 1 starts. Expect the core 1 Guru report with PC in `app_cpu_main`. The run does not reach DONE (core 0 stops), so cap it with `timeout`, and kill any leftover `cat_until`/`cat` readers.
  - `4`: `3` without the reclaim, as the control. Its output should match `3`.
  - If the ROM layout looks different, check it: `xtensa-esp32s3-elf-objdump -h ~/.espressif/tools/esp-rom-elfs/*/esp32s3_rev0_rom.elf` (`.stack_app`, `.bss_ets` … `.bss_xtos`, `.data_xtos`) and `nm -n` for `xtos_exc_handler_table`.
- **If the guard fires or a probe disagrees:** stop reclaiming, either by dropping the `reclaimRomAppCpuBootDram()` call or by leaving the reservation alone, then re-measure. A sturdier alternative not yet tried: boot core 1 from an early `ESP_SYSTEM_INIT_FN`, before IDF recycles the ROM DRAM, and park it in an IRAM spin loop on a static stack until `setup()` releases it.

## Follow-up TODO

- **A DOS 2 d1.atr.gz as D1 stopped a real 800XL's SDX boot (bookmarked 2026-11-14; cause found, fix to soak).** SDX, booting any D1 without an SDX boot sector (none, single or double density), stores to `$D5B9` (the R-Time 8 clock's registers). A Maxflash 1 Mbit cart decodes only `$D500-$D51F` (atari800's ATMAX_128 ignores the rest), but core 1 latched every `$D5xx` write's offset and mapped `& 0x1f` = 0x19, cart off, under SDX's feet. Reproduced in csim with BUS_CYCLE=1 by the user (gdb on core1.cpp's latch). Fixed in core 1's write path: `lastPageOffsetIndex()` sends a write with offset bits 5-7 set to an unread slot (`extui` + `movnez`, +2 cycles, `wrSampleNops` 10 -> 8 so P5 stays at 69); core 0's `accessD500()` got its matching check back. csim BUS_CYCLE: d1.atr.gz 3859 I/Os in 90 s (9 without the fix), toolkit unchanged; bench FAKE_SIO PASS. Still to do: a real-Atari soak, then d1.atr.gz back as D1 in the configs. Also: `tools/prepare_spiffs_disk.sh` only adds files to an existing image, and the images are untracked, so each machine's d1/d2 drift (d2 is single density on .1, double on a24); build them from scratch.

- **Core fetch and OTA speed, compression (bookmarked 2026-11-14; right after the master merge).** A stored core fetch runs ~28 kB/s (32 KB stdio buffer + SPIFFS write cache; was ~7 kB/s), against ~490 kB/s for a test object over the link, so a full 2.2 MB dump takes ~80 s. In order:
  1. **Measure first:** a `fetch core` variant that hashes but doesn't write, plus timers around the sink's write and hash. Candidates: SPIFFS writes, main's `esp_flash_read()` of 281 bytes per chunk in diagnostic mode (the test object comes from RAM; if this is it, read ahead in big blocks on main), the per-chunk SHA.
  2. **Gzip the stored core on the Sidecar as it writes** (miniz `tdefl`, low level, state in PSRAM; SHA check still on the uncompressed stream). Full dumps are mostly PSRAM heap: expect 5-10x, so fewer SPIFFS writes and room to keep the previous core (helps the lost-core risk below). Name it `main-<token>.core.gz`: the "already fetched" compare stays a filename check. `crash_bundle.sh` gunzips before `coredump-info`.
  3. **`app.bin.gz` as the OTA Firmware object:** about half the spiffs and half the OTA transfer; main inflates as it writes the OTA slot (it already inflates `.atr.gz`). The app token (offset 0xb0, the app description) comes from inflating just the first ~200 bytes, so no `.hash` file and no way for two files to disagree.
  4. **sidecar_serial_flasher:** `flash_spiffs.sh` keeps bootloader, partition table and OTA data raw beside `app.bin.gz`; the flasher inflates the app as it sends it (later: the ROM's `FLASH_DEFL_BEGIN` takes zlib, not gzip, so it would need a conversion).

- **A fetched core can be lost (bookmarked 2026-11-14).** After the Sidecar fetches, verifies and stores main's core (`/spiffs/core/main.core`), it has main erase it (EraseCore, diagnostic mode), so main's next boot report shows none. From then on the Sidecar's spiffs holds the only copy, until `boot.sh -sc`'s `crash_bundle.sh --sidecar` has dumped that spiffs, pulled the core out and bundled it. If that fails (esptool, the extractor, tar), or the next `-sc` run restages the spiffs first, the core is gone. Being thought about: detecting a stale core file without erasing main's. The likely fix, stateless: `-sc` packs the previous `core/main.core` back into the new spiffs image, so the Sidecar sees it (its SHA token equals main's `coreVersion`) and doesn't refetch; the last core then stays in the spiffs until the next crash overwrites it, and main's copy needn't be erased.

- **Boot-time pin hazards on the main board (bookmarked 2026-11-11; fix even though a year of running hasn't damaged anything).** Data is `Pin<38, 8>`, GPIO38–45 = D0–D7, so two of the S3's boot pins are Atari data lines:
  - **GPIO43 = D5 = U0TXD.** Three sources, worst first:
    1. IDF's console was UART0 (`CONFIG_ESP_CONSOLE_UART_DEFAULT=y`, 115200, USB-Serial-JTAG secondary), so the second-stage bootloader's log and every early app printf toggled D5 on every boot. **Fixed (2026-11-11):** USB-Serial-JTAG is now the only console; bench-booted to DONE. Still to confirm on a real Atari: serial commands (`halt.sh`'s `exit 2`, read only in the PBI handler) and a panic's backtrace/core dump in a crash bundle.
    2. The ROM banner: already off. `CONFIG_BOOT_ROM_LOG_ALWAYS_OFF=y` burns `UART_PRINT_CONTROL` on each board's first boot; confirm with `espefuse.py summary`.
    3. The pad's default state: at reset GPIO43's function is U0TXD, so it may sit driven high with nothing printing, until the app reconfigures it. Related observation (2026-11-14, FAKE_SIO's bank-op probe, the app running, R/W held high, the data lines pulled low): on the isolated bench board E8:F6:0A:D1:CC:CC, D5 reads high; on the a24 pair's main E8:F6:0A:D2:EE:78, D5 and D6 read high now and then (over 2000 samples), with GPIO43/44 on their GPIO function and never output-enabled by the ESP. Something outside the ESP drives them, presumably the dev boards' USB-UART bridge on U0TXD/U0RXD. Note D6 = GPIO44 = U0RXD too. FAKE_SIO now has core 1 drive the data lines for its PORTB writes. Measure with a weak pull-down plus a scope, or a Sidecar sampling it, across a main-board reset with no Atari attached. If it's driven, a second-stage bootloader hook that makes GPIO43 an input first thing shrinks the window to the ROM's few ms; the ROM part can't be changed in software.
  - **GPIO45 = D7 = the VDD_SPI strap.** At reset it picks the flash supply voltage; if the Atari holds D7 high while the ESP resets, the chip may select 1.8 V flash and fail to boot. **Handled (2026-11-11):** `tools/boot.sh` runs `tools/efuse_check.sh` with the Atari off, which burns `set-flash-voltage 3.3V` (irreversible) on any S3 without it, unless its PSRAM is a 1.8 V part. The bench board already had it burned at the factory; the burn path was tested on a virtual eFuse chip. Check each pool board's boot log for the `efuse_check:` lines.
  - Related, not a hazard: GPIO46 is MPD and a strap; download mode needs it low, so ROM download mode works only with the Atari powered off.
