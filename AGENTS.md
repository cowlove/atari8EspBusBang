# Repository Guidance

## Firmware Smoke Tests

- Prefer `tools/boot.sh` for routine hardware build/flash/boot tests rather than invoking `idf.py flash` directly. It records timestamped serial output under `stash/` along with the Git version and a working-tree diff, providing a useful history of boot behavior.
- `boot.sh -DBOOT_CONFIG=SDX_AUTO` works as is: boot.sh adds the C string's quotes when they're missing (`'-DBOOT_CONFIG="SDX_AUTO"'` and `-DBOOT_CONFIG=\"SDX_AUTO\"` still work); the same for `-DHW_TYPE=` and `-DCART_IMAGE=`. Not for the split form `-D BOOT_CONFIG=...`.
- If the project-root IDF build cache is stale or points at an unavailable toolchain/source path, run `idf.py fullclean` from the project root, then continue with `tools/boot.sh`. `fullclean` removes generated build state only; it leaves source files and boot logs intact.
- This reproducible history is worth the inconvenience that `boot.sh` may leave serial-monitor processes running. After each run, check for stale monitors and terminate them before starting another capture.
- The script snapshots `git diff HEAD` and `git describe`, so the diff includes both staged and unstaged changes to tracked files. Untracked file contents are not included; account for those separately when they matter to a capture.
- `boot.sh -sc` updates and boots main through the Sidecar (`tools/boot_sidecar.sh`): it builds main, builds and flashes the Sidecar app plus its spiffs with main's images staged (on `SIDECAR_PORT`), resets the Sidecar, then runs `cat_until` on the Sidecar's console. **The Sidecar sequences main's boot** (2026-11-25, `sidecar/main/main.cpp`, `mainReset.h`): first thing in `app_main()` it holds the Atari's RESET and main's EN low, and once its setup is done (link up, service task started) it prints `Sidecar: ready; main released from reset: it boots now` and releases EN: every Sidecar start reboots main, in sequence. (Before, `boot_sidecar.sh` waited for a `sidecar: 1s:` stats line, off by default since 2026-11-23, so it sent its `reset` only at its 60 s timeout: ~40-60 s with main running whatever it had and the Atari held.) At main's boot report (BootStatus) the Sidecar compares main's app token (the ELF SHA-256's first 4 bytes, `appVersion`) with the staged `app.bin.gz`'s, and if they differ has main install it by OTA over the link (FetchFirmware; app only, needs `ota_1`). Builds carry no compile time (`CONFIG_APP_COMPILE_TIME_DATE` off), so an unchanged main isn't reflashed; `-DBOOT_TOKEN=<n>` (main prints `BOOT_TOKEN n`) forces a new image, for soaks of repeated updates. main's output, DONE included, reaches the Sidecar's console over the link, so `-sc` builds main with `-DSIDECAR=ON` (a CMake option in the top-level `CMakeLists.txt`, with `SIDECAR_LOOPBACK` and `SIDECAR_LOG_ONLY`; no longer sdkconfig, 2026-11-22): any other `boot.sh` run builds without the Sidecar unless given `-DSIDECAR=ON`. **DONE lines** (2026-11-25): every one, main's and the Sidecar's, is `DONE <sec> <flag> <reason>`, flag < 0 a failure (the pool's monitoring scripts parse it). Main's flags: the exit reason's leading number (`core0_exit()`): -1 watchdog, -2 IO timeout, -3 stackprog timeout, -4 repeat reads, -6 startup timeout, -9 TEST_FAIL_EXIT, -10 CORE1_FAULT/HANG; 0 run time reached, 1 exit hotkey, 2 exit command, 3 user-requested halt, 4 telnet exit, 5 ProcFS HALT file. The Sidecar's (`printDone()`, sidecarApp.cpp; `<sec>` since the run's boot report; the reason starts `Sidecar:`): -11 main crashed (core fetched), -12 main silent on the link (reset, no core), -13 main silent and no boot report after the reset, -14 main silent (csim, no reset), -15 ERASE_CORE failed. **Power-off on exit** (2026-11-25): boot.sh powers the Atari off on any exit (`boot_power_off_at_exit`, chained into every EXIT trap of boot.sh, boot_sidecar.sh and boot_net.sh; INT/TERM/HUP exit through it too): main has exited or is unwatched by then, so the Atari isn't left running against an unserved bus between runs. **Power-on** (2026-11-25, `tools/power_on_when_up.sh`): plain `boot.sh` powers the Atari on at main's `BOOT COMPLETE`, or blindly 10 s without it (`POWER ON BLIND: ...`: main's console output was lost; main waits only 2 s for a USB host); `-sc` at main's `BOOT COMPLETE` or the Sidecar's `BOOT_EXPECTED_COMPLETE` (printed 5 s after a boot report that leads to a normal boot, no OTA, core fetch or diagnostic mode, if main's BOOT COMPLETE hasn't come; the Sidecar holds the Atari's RESET until it does), never blind (an OTA can be in progress), giving up after 120 s. After DONE the capture reads on (`cat_until.sh -a/-w`, the same reader) to the Sidecar sampler's report of the run's last period, ending `SAMPLER_PERIOD_END ... stop` (main stops the sampler with SampleControl just before its exit report), for at most 10 s. Exit 3 if main never runs the staged app, 5 if what it runs isn't this build, 7 if main went silent on the link. **Main's link watchdog, on the Sidecar** (2026-11-22): the Sidecar's console output keeps `cat_until`'s idle timeout from ever firing, so a main that hung or lost its link never ended the run. The Sidecar now ends it: armed by a normal boot report, disarmed by main's DONE, reset by any command main sends (a running main sends one at least every ~2 s: its status line and ConsoleIn poll); silence for 30 s beyond main's own timeouts (the boot profile's `ioTimeoutSec`/`wdTimeoutSec`; off if `ioTimeoutSec` <= 0; since 2026-11-25, so a main still counting reaches its own failure exit and core dump first) prints `MAIN_LINK_SILENT`, resets main into diagnostic mode, and its boot report decides: a core dump is fetched and bundled as for any crash (exit 6), none gives `DONE <sec> -12 Sidecar: main silent ...` (exit 7). Test with `-DTEST_CORE0_HANG=<n>` (core 0 spins with interrupts masked: silent, no reboot). main's own SPIFFS, bootloader and partition table, the eFuse check and the crash bundle are skipped in this mode. `boot.sh -sc -qq` builds and flashes nothing: it resets the Sidecar over its USB (esptool `run`), whose start then reboots main as usual, and captures the run: both boards boot afresh (new link initial conditions) on the images already there (`tools/bench_soak.sh` loops on it).
- `boot.sh` no longer deletes `build/`: `tools/clear_build_defines.sh` clears from its CMake cache every `-D` setting `main/CMakeLists.txt` reads (options, CACHE variables, the define list) that this run doesn't pass and that differs from its default, so nothing carries over and builds stay incremental. A new `-D` knob goes in `main/CMakeLists.txt`'s list, where the cleaner finds it; the Sidecar's knobs (`SIDECAR_DEFINES`) are cleared by `boot_sidecar.sh` the same way.
- **Serial-flashing main: the Sidecar console's `flash`, by hand only** (`sidecar/main/mainFlasher.cpp`; the standalone `sidecar_serial_flasher/` app is gone, 2026-11-21): for initializing new boards, with the main board disconnected from the Atari (download mode needs MPD low; refused while phi2/D0/D1 show activity, so park a `FAKE_CLOCK` main first, e.g. in diagnostic mode). `flash main yes [<spiffs image>]` writes the bootloader, partition table, otadata and app staged in `/spiffs/main/` (`sidecar/flash_spiffs.sh`), then main's spiffs from the image if given; `flash spiffs yes <image>` only the spiffs (its partition from the staged partition table); `.gz` images are inflated as sent. Main's spiffs image: `tools/flash_spiffs.sh --noflash` builds `spiffs/spiffs.bin`; gzip it and `tools/sidecar_xfer.py put` it to `/sd`. No script runs it. Staging a new `app.bin.gz` in the Sidecar's spiffs is the deliberate act that updates main, by OTA. The Sidecar app's console `reset` is a plain EN reset, unchecked (it works with an Atari attached).
- **Crashes in `-sc`:** main's panic text only reaches main's own console, so the Sidecar learns of a crash from main's next boot report (a core dump it hasn't stored). It puts main in diagnostic mode, fetches the core into its spiffs, gzipped on the fly by a writer task (`/spiffs/core/main-<token>.core.gz`; "already fetched" = a stored file named with main's `coreVersion`, no other state), has main erase its copy (EraseCore; see the TODO on losing a core) and prints `COREFILE_AVAILABLE main <path> <bytes> <token>` then `DONE`. `tools/crash_bundle.sh --sidecar` then dumps the Sidecar's spiffs with esptool, pulls the core out (`tools/spiffs_extract.py`), gunzips it and decodes it against main's ELF. A `Backtrace:` on the Sidecar's console is the Sidecar's own crash: its own coredump partition (`sidecar/partitions.csv`), decoded against `sidecar/build/sidecar.elf`. Every bundle carries both apps' builds. **Core 1 failures** (2026-11-22): core 1 runs on the ROM's vectors, whose fatal handler only prints on the ROM UART and spins, so a core 1 fault used to leave main hung (no reboot, no boot report, the run ending at its `RUN_SEC+600` timeout). Now core 1 installs its own handler in the ROM's xtos C handler table (`core1ExceptionHandler()`, `main/main.cpp`; the table is in the reserved `.data_xtos`), which records EPC1/EXCCAUSE/EXCVADDR and parks core 1. Core 0 checks once a second that the bmon heads move; 3 s without, with phi2 running, it exits with `-10 CORE1_FAULT: ... at PC ...` (the recorded fault) or `-10 CORE1_HANG: ... core 1 PC ...` (samples from the assist-debug unit's PC record), a failure exit: report, DONE, core dump, fetch, bundle. phi2 stopped (an Atari off) is logged once, not a failure. Test knobs: `-DTEST_CORE1_FAULT=<n>` (core 1's block tables wild for 1 ms; not with FAKE_SIO, whose core 0 code reads them too) and `-DTEST_CORE1_HANG=<n>` (core 1 stalled), once per boot that didn't follow a panic. **Cores from an older build:** every main build's ELF is kept in `stash/elf/<sha256>.elf.gz` (`tools/elf_archive.sh`, the newest 40); `crash_bundle.sh` checks the core's app SHA (`tools/core_app_sha.py`) against `build/`'s ELF and, on `CORE_ELF_MISMATCH`, decodes against the archived one (bundled as `<prefix>.elf.gz`).
- **`boot.sh -sc --erase-core`** (bringing up a board, or a core that can't be fetched, which otherwise loops: every boot asks for it again): builds the Sidecar with `-DERASE_CORE=1` (a cache knob, cleared by the next run without it). It deletes the cores stored in its spiffs at startup, and a core in main's boot report is erased in main's flash (EraseCore, retried as `sidecarFetch()` does), never fetched, then main is reset and the run goes on (a staged OTA included). The run's read-on after a failure exit stops at `ERASE_CORE: erased`. Needs a Sidecar build (not `-qq`).
- **The Sidecar over the network** (2026-11-25; `sidecar/main/sidecarWeb.cpp`'s header lists the API): files: `curl -f --data-binary @<local> "http://<sidecar>/files/put?p=/sd/<name>"` (`/spiffs/...` too; `.part` then renamed; replies `{"size":n,"sha256":hex}` of what it received), `GET /files/get|hash|ls?p=`, `POST /files/rm?p=`, `main:/spiffs/...` in main's diagnostic mode. Console: `POST /console/cmd` (each body line runs as if typed, echoed `web> ...`; `recv`/`send` refused; replies `{"queued":n,"at":offset}`), `GET /console/out?since=<offset>[&wait=<ms>]` (everything the Sidecar prints, main's proxied output included, from a 64 KB ring in internal RAM; headers `X-Console-Next`, `X-Console-Lost`; the server takes one request at a time, so `wait` holds it: one script only), `/console` an interactive page. stdout is replaced by a line-buffered picolibc bufio stream (`sidecar/main/consoleTee.c`, installed by `sidecarConsoleTeeBegin()` first in `app_main()`; picolibc's `stdout` is one global) that hands each line to the ring (a spinlock, not a mutex: printf can come from anywhere) and then writes it to the console's fd. Not `funopen()`: its stream ignored `setvbuf(_IOLBF)`, so lines sat in 256-byte blocks until more output came (a quiet Sidecar then looked hung to a client waiting for a line). Debug: `POST /debug/abort` (a deliberate panic: a core dump of every task, then a reboot), `GET /debug/coredump` (the Sidecar's coredump partition, raw: `esp-coredump info_corefile -t raw -c <file> sidecar/build/sidecar.elf`).
- **The Sidecar's web server in csim** (2026-11-25): the real `sidecarWeb.cpp` handlers on `http://localhost:8080` (`CSIM_HTTP_PORT`, 0 none; `csim/a800/csim_httpd.cpp`: one request per connection, polled from the Sidecar's service loop, so `/console/out`'s `wait` is ignored); files in `./webfs/{sd,spiffs}` (`CSIM_WEB_ROOT`); `/console/out` carries csim's stdout (both apps' and atari800's, from the Sidecar's start: a glibc cookie stream feeding the same ring, `sidecarConsoleTeeBegin()`); no `/debug/*`, no self-install in `update`. **`CSIM_REALTIME=1`** paces the simulation to the wall clock (csim otherwise runs a 40 s run in ~1 s, too fast for a client): e.g. `. tools/export_build_env.sh; cd csim/a800; CSIM_REALTIME=1 RUN_SEC=600 ./run.sh`, then curl or a browser. (`run.sh` needs `atr` on PATH: source `tools/export_build_env.sh` first.)
- **`boot.sh -net <sidecar host>`** (`tools/boot_net.sh`, 2026-11-25): build both apps as `-sc` does, upload `main.bin.gz` and `sidecar.bin.gz` to the Sidecar's `/sd/update` when it has an SD card (`GET /files/ls?p=/sd` answers), else `/spiffs/update` (`NET_UPDATE_DIR` overrides; SHA-256 checked; the old image removed first, one retry; the put makes missing directories), send `update /spiffs/update` (`POST /console/cmd`), then follow `/console/out` into the capture (through the Sidecar's restart: an offset going backwards means it restarted) to main's DONE; power-on at main's BOOT COMPLETE or the Sidecar's BOOT_EXPECTED_COMPLETE. Exit codes as `-sc` (3 update failed or main never ran this app, 4 no DONE / Sidecar unreachable, 5 another app, 6 main crashed: its core is fetched over the web into `<prefix>.core.gz`, 7 main silent). Nothing over USB, so for machines with only the network; the Sidecar's bootloader, partition table and spiffs still need one USB flash (`-sc`). The Sidecar console's **`update [<dir>]`** (`sidecarApp.cpp`, UpdateJob): images `main.bin.gz` and `sidecar.bin[.gz]` from `<dir>`, else `/sd/update`, else `/spiffs/update`; one already running is skipped. Main first: staged as the Firmware object (`/spiffs/main/app.bin.gz`), main reset, the usual OTA; when main reports the new app, it is held in diagnostic mode while the Sidecar writes its own image into its spare OTA slot (~25 s, gunzipped as it goes), switches slots and restarts (an RTC_NOINIT flag makes the new app reset main once up). Ends `UPDATE_DONE ...` or `UPDATE_FAILED <why>`. **Rollback** (`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`, the Sidecar): a newly OTA'd app is on probation until healthy (up 30 s with WiFi connected, or WiFi off in the profile), then marks itself valid; not within 180 s, it restarts and the bootloader goes back (tested on the a24 bench with `SIDECAR_DEFINES=-DTEST_UNHEALTHY=1`, an image that never marks itself valid: back on the previous slot's app after 180 s; its image stays in `/spiffs/update`, so a later `update` would install it again). **Main's image is served from the update directory** (2026-11-25): `update` points the Firmware object (`AtariService::firmwarePath`) at the `main.bin.gz` it found, no copy into spiffs; main fetches it by the same OTA object as ever. A Sidecar restart puts it back at `kFirmwarePath` (`/spiffs/main/app.bin.gz`, `-sc`'s staging), and once main runs the update's app an older, different image there is removed (`dropStaleStagedApp()`: else the next boot would OTA main back to it), so after an update main's boot report can say `main app <x>; no app staged in ...`: boot_net.sh and boot_sidecar.sh accept it as well as `is the staged app: current`. **`MAIN_UPDATE_STALLED`**: no firmware chunk asked for 15 s during main's OTA resets main (its next boot report then says MAIN_UPDATE_FAILED) instead of hanging the run. `SIDECAR_DEFINES=-DBOOT_TOKEN=<n>` forces a new Sidecar image (`Sidecar: BOOT_TOKEN n`; boot.sh's own `-DBOOT_TOKEN` is main's).
- **SetFlags: the Sidecar posts flags into main** (2026-11-25, `SidecarCommand::SetFlags`, `SidecarMainFlag` in `components/sidecar_link/sidecar.h`): main's hot link poll (every 100 ms in `core0Loop()`) records them (memory only), and the loop acts on them right after the poll (`takeMainFlags()`). One-shot `Interrupt` (0x1): `raiseInterrupt()` once, to get the 6502 into main's PBI handler in a boot profile that neither schedules interrupts nor does I/O. Sidecar console: `setflags interrupt` (or a number), answered `main has them (pending ...)`. Tested in csim bus-cycle mode (`MODES_CSIM_BUS`, no interrupts of its own: `CSIM_SIDECAR_CMD="@10 setflags interrupt;@20 setflags interrupt"`, the io: line's irq count 0, 1, 2); not yet on hardware.
- **Screenshots in the Sidecar's web page** (2026-11-25): `SidecarMainFlag::Screenshot` (0x2) sets `screenshotRequested` after main's poll; the cold PBI handler's next IRQ call (pbi.cpp, beside `telnetScreenRun()`) sends one (`screenshotToSidecar()`, main/screenshot.cpp): `dumpScreenshot()`'s text, now written through a sink (`dumpScreenshotTo()`), as one session on the `Screenshot` stream channel (`SidecarChannel::Screenshot`, main's 2 KB TX ring pumped back to back: ~8 KB in ~60 ms in csim). The Sidecar keeps the latest whole one (`screenshotPoll()`, `sidecarScreenshotLatest()`; a 16 KB RX ring); `GET /screen/data` serves it, `/screen` (SCREEN in the menu bar) renders it on a canvas (a port of `tools/screenshot_png.py`; charset bytes main can't read at $E000-$E3FF, the Atari's own OS font, come from AltirraOS's font, embedded with its permissive notice); Capture posts `setflags screenshot interrupt` (Interrupt for profiles that raise none). `setflags` retries for 3 s: main's own commands preempt the Sidecar's (Preempted, served, asked again). Screenshots need bus-cycle csim (`BUS_CYCLE=1`), as the shutdown one does.
- **`tools/bench_net_soak.sh [-H host] [-t 180] [-n runs] [-m both|main|sidecar]`** (2026-11-25): back-to-back `boot.sh -net` FAKE_SIO runs on the bench pair, each with new `BOOT_TOKEN`s (the run's start time) so every run updates main by OTA and the Sidecar itself; a line per run in `stash/bench_net_soak.summary` (ANOMALY: rc, no PASS, no OTA/no Sidecar update, update failed, crash; the anomaly's boot.sh output kept). Host from `-H` or `SIDECAR_HOST` (tools/config); stop with `touch stash/bench_net_soak.STOP`.
- **Debugging a Sidecar with OpenOCD** (a24, udev rule installed 2026-11-25): `openocd -c "set ESP_RTOS FreeRTOS" -f board/esp32s3-builtin.cfg -c "adapter serial <MAC>" -c "gdb_memory_map disable"`, then `xtensa-esp32s3-elf-gdb -ex "target extended-remote :3333" -ex interrupt -ex "thread apply all bt" sidecar/build/sidecar.elf`: every task's stack, on a running board. With memory protection on (`CONFIG_ESP_SYSTEM_MEMPROT`, the default) a gdb attach resets the chip: turn it off in `sidecar/sdkconfig` for such a session. Breakpoints in flash need `hbreak`. With a USB host attached, IDF treats the chip as debugged: a panic sets a breakpoint and returns (no reboot, no core).
- **OTA chunk timeouts (fixed 2026-11-25).** Main's fetch waited 200 ms per chunk and gave up the whole OTA on one timeout; the Sidecar `stat()`ed `app.bin.gz` for every chunk, which on the 9.9 MB spiffs sometimes took longer: 4 of 8 OTAs stalled (main left in diagnostic mode, silent; the run hung to its timeout). Now ReadChunk uses the file ReadVersion opened, and `sidecarFetch()` retries a timed-out request up to 10 times: 8 of 8.
- **Files to and from the Sidecar** (its `/spiffs` and `/sd`): `tools/sidecar_xfer.py put <local> <remote>` / `get <remote> <local>`, over the Sidecar's USB console (nothing else may hold the port: no `cat`, no `-sc` capture running). SHA-256 checked end to end; about 510 KB/s up, 220 KB/s down. The console also has `ls`, `rm`, `cp`, `gunzip` and `sdformat yes`. **Files to and from main's spiffs:** `tools/main_xfer.py put <local> /spiffs/<name>` / `get /spiffs/<name> <local>` (via a staging file on the Sidecar's `/sd`, then the console's `cp` to `main:`; SHA-256 checked with `hash main:`). Main serves its files only in diagnostic mode (console `diag`, then `reset`). The console's `cp`/`ls`/`rm`/`hash` take `main:` and `sidecar:` prefixes (none: the Sidecar).
- `-DTEST_PANIC=<n>`: main's core 0 crashes (a wild store, hot) once `elapsedSec` passes n, once per boot that didn't follow a panic: for testing the core dump path, e.g. `boot.sh -sc -t 30 -DTEST_PANIC=20`.
- **Failure exits dump core.** A run whose exit reason is negative (`-2 IO timeout`, `-3 stackprog timeout` ...) prints its report and its usual `DONE <sec> -<n> ...` line, then panics (`EXIT_COREDUMP`, `main/main.cpp`), so it leaves a core dump of the state it failed in. `boot.sh` reads on after a negative DONE to the panic's `Rebooting` (then `crash_bundle.sh`); `-sc` reads on to the Sidecar's fetch (`DONE <sec> -11 Sidecar: main crashed`) and exits 6 like any crash. `-DTEST_FAIL_EXIT=<n>` forces one (`-9 TEST_FAIL_EXIT`) once `elapsedSec` passes n: the timeouts are off in FAKE_CLOCK builds.
- **Screenshots from the shutdown report** (2026-11-22): after the text-screen dump (`SCREENB`), `dumpScreenshot()` (`main/screenshot.cpp`, which documents the format) prints the ANTIC/GTIA registers as last written (`d000Write[]`) and their shadows, the display list (hex, then decoded `dl:` records), each mode line's `screenmem:` and, with text modes on screen, the `charset:`; `tools/screenshot_png.py <log> <out.png>` renders it (stdlib only; approximate NTSC palette; no DLI changes, players/missiles or fine scroll). For regression boots of cartridges that never use the PBI device or the console. Only what the board serves is readable: cartridge ROM main serves, mapped RAM; native RAM and the Atari's OS ROM read `--` (so the OS font needs `--font <OS ROM or 1 KB font>`, and screen memory in native RAM, e.g. AUTO's small base RAM on a 48K+ machine, is lost). Not in `FAKE_CLOCK` builds (no ANTIC). csim: bus-cycle mode only (the default mode ends without core 0's report); `csim/a800/run_modes.sh` runs `make_modes_cart.py`'s cartridge (a band of each ANTIC mode, all in ROM; boot config `MODES_CSIM_BUS`) and renders `build-atari/modes.png`.
- `boot.sh` refuses `-DFAKE_CLOCK` and `-DFAKE_SIO` builds (and `-qq` when the cached build has them) on any machine whose `tools/config` sets `MQTT_HOST` and `TAS`, i.e. one where it powers on a real Atari. Both are bench-only: FAKE_CLOCK drives the clock, R/W and A0, and FAKE_SIO's bank ops rewrite the bus pins' pulls and R/W's routing from core 0 while core 1 is hot (`main/fakeSio.cpp`).

## Link timing (exp-txalign, 2026-11-19)

How the i2slink's latency works and what tunes it (details in `components/i2slink/src/i2slink.c`).

- **The component.** `components/i2slink/` is a git submodule (since 2026-11-23): its own repo, https://github.com/cowlove/i2slink (branch `main`; history extracted from this repo's, back through `components/sidecar_link/` and `main/`). A link change is a commit there (push it), then a submodule pointer bump here; after pulling, `git submodule update --init components/i2slink`. A standalone ESP-IDF component: `include/`, `src/`, `idf_component.yml`, `README.md`, `LICENSE` (GPL-2.0), `examples/pingpong` (PING/PONG/LOOPBACK; LOOPBACK runs on one bare board). Keep it free of this project: no a8log, no `CONFIG_A8BB_*`, no project names in its API. Logging goes through `i2slink_config_t::log` (`SidecarPeer::begin()` passes a `LOG()` wrapper), hot placement through `I2SLINK_HOT_SECTION` (set by the top-level `CMakeLists.txt`), and csim's hooks through `I2SLINK_SIM_*` (`csim/a800/include/csim_c_prelude.h`). Its comments are project-neutral too (no main, Sidecar, core 1, csim, bench names): keep them that way.

- **Slots.** Each end's TX DMA loops over its cycle (468 bytes, ~374 us); a new version leaves when that DMA reaches H: one fixed instant per cycle, the end's "slot", a fixed distance from the peer's (one BCLK). A request waits 0..1 cycle for its own slot (random: the 6502 decides when); the Sidecar's wait for a fast response is a constant set by where the boot left the frame.
- **Variable-length frames.** A version uses only its length (`i2slink_write(link, payload, length)`; SidecarPeer trims trailing zero words), and its CRC and T follow it, so a short frame ends early and the reader's end tripwire follows T. A wire-format change: an old main and a new Sidecar can't talk (no OTA across it).
- **Slot tuning** (the Sidecar, on by default): measures each fast response's wait (written within 256 us of its command: RAM answers; SD-bound ones take 512 us and up) to its TX slot and moves its frame to where a window of 32 would have waited least, a response landing just after the slot (or within 12 us before it) counting the whole cycle. Moves need two windows agreeing within 40 us. The wait comes from the TX GDMA's descriptor register, which runs `I2S_DMA_TX_DESC_LEAD` = 2 descriptors (~56 us) ahead of the data it sends (measured; csim models it).
- **Announced moves.** A move would break main's lock (a search on a half-rewritten ring cost a command ~4.7 ms). The Sidecar announces it in its report word and moves when main echoes (250 ms timeout: main polls the link ~every 50 ms); main, on framing failure, takes its old marker moved by the announced amount if framing holds there. Bench: main's lock count stays 1 through a run.
- **The ack skip.** The Sidecar's `service()` doesn't ack a command it answers at once; the response carries the ack (one frame write instead of two). main's poll paths still ack at once.
- **The wire rate is 200,000 frames/s (RX on the rising edge) until the carrier boards arrive (decided 2026-11-20).** Every wiring change moved the clean maximum: with the bench pair's RX moved to GPIO18, next to R/W toggling under FAKE_CLOCK, 312,500 relocked thousands of times a minute (clean with no bus clock); 200,000 was clean. The timings below were measured at 312,500.
- **Where a round trip goes** (a24 bench, Nop, tuned: min 442 / mean 641 us): main's own slot wait (0..374, random), two hops of ~170-205 us each (~58 us the frame on the wire, ~147 us the I2S TX FIFO, which the GDMA keeps full: no depth setting, only the wire rate scales it), the Sidecar's read-to-write ~75 us (its write's bit-shift render is ~60 us of that) and a ~25 us slot margin. Bulk fetches run at 3 wire cycles a chunk (233.6 kB/s), bound by main's side (~350 us of its own work a chunk).

## ROM core 1 boot DRAM

`startCpu1()` boots core 1 through the ROM, in DRAM that single-core IDF otherwise recycles into the heap. `main/main.cpp` reserves 0x3fceb710–0x3fceee34 (`rom_app_cpu_boot`) and, once core 1 reaches `app_cpu_main()`, returns all of it except `.data_xtos` (0x3fcedf60–0x3fcee378) to the heap: 13,068 of 14,116 bytes. This depends on how the ROM and IDF handle core 1 today, so treat it as fragile:

- **What it relies on** (measured 2026-11-06 with ESP-IDF 6.1, ESP32-S3 rev 0.2):
  - The ROM's core 1 boot writes only `_Pri_4/_Pri_5_HandlerAddress` (0x3fcee370..0x3fcee378, inside `.data_xtos`). On a cold boot and after a panic reboot, nothing else in the span changes, then or later.
  - Core 1 keeps the ROM's vectors. Faults dispatch through `.data_xtos` (`xtos_exc_handler_table` etc.), which is why it stays reserved. With it intact, a core 1 fault prints `Guru Meditation Error: Core 1 panic'ed` with the faulting PC, and core 0 then stops (no reboot), whether or not the rest is reclaimed. With those tables overwritten, the result depends on the garbage: either a core 0 "Cache error" panic or a silent core 1 death.
  - `startCpu1()` runs once per boot, and the panic hook stops core 1 instead of restarting it, so the ROM never boots core 1 again over the heap.
- **Boot-time guard:** before `startCpu1()`, the reclaimable parts are filled with 0xa5. They are reclaimed only if the pattern survives core 1's boot. Otherwise the boot prints `ROM DRAM reclaim: ... keeping the span reserved` with the changed spans. The normal boot line is `Reclaimed 13068 bytes of ROM core 1 boot DRAM`. The guard cannot see a change that makes core 1 depend on the reclaimed DRAM after boot, so rerun the probes below after any IDF, ROM-ELF or chip-revision change, or any change to `startCpu1()`, `app_cpu_init()` or the panic hook.
- **Re-verification** on the isolated bench board, with `PORT=<by-id> ./tools/boot.sh -t 40 -DFAKE_CLOCK=1 -DBOOT_CONFIG=\"BENCH\" -DROM_BOOT_PROBE=N`. Afterwards, `cmake -U ROM_BOOT_PROBE build` clears the cached define.
  - `1`: what core 1's boot changes in `.data_xtos` (snapshot diff; expect 0 bytes, because the ROM rewrites the same values) and in the reclaimed parts (expect 0), and again 3 s later. Then an 8 KB allocation should land in the reclaimed part, and the heap integrity check should pass.
  - `2`: `1`, then one `abort()`. Expect a core dump and a panic reboot, the same results again after the reboot, and DONE.
  - `3`: `1`, then a core 1 store to address 4, 5 s after core 1 starts. Expect the core 1 Guru report with PC in `app_cpu_main`. The run does not reach DONE (core 0 stops), so cap it with `timeout`, and kill any leftover `cat_until`/`cat` readers.
  - `4`: `3` without the reclaim, as the control. Its output should match `3`.
  - If the ROM layout looks different, check it: `xtensa-esp32s3-elf-objdump -h ~/.espressif/tools/esp-rom-elfs/*/esp32s3_rev0_rom.elf` (`.stack_app`, `.bss_ets` … `.bss_xtos`, `.data_xtos`) and `nm -n` for `xtos_exc_handler_table`.
- **If the guard fires or a probe disagrees:** stop reclaiming, either by dropping the `reclaimRomAppCpuBootDram()` call or by leaving the reservation alone, then re-measure. A sturdier alternative not yet tried: boot core 1 from an early `ESP_SYSTEM_INIT_FN`, before IDF recycles the ROM DRAM, and park it in an IRAM spin loop on a static stack until `setup()` releases it.

## bmon: core 0 must keep up

Core 1 pushes every bus cycle into the bmon ring (512 entries, ~0.3 ms of bus) and never waits. The bmon loop, `core0_onBmonChange()` and `core0_utilityTasks()`, must keep up and drop nothing, except inside `handlePbiRequestHot()`, where entries may be lost and the backlog is discarded on return. That exception is safe only because the 6502 is then in our PBI driver with interrupts masked, so it makes no write core 0 must act on, in particular the `$D1FF`/`$D301` writes that assert halt_ (only `resume6502()` releases it; a lost one hangs the 6502). New core 0 work that can run for more than a few hundred bus cycles outside a request, or a new reason for the 6502 to write those registers during one, breaks it. Full statement at `bmonArray` in `main/bmon.h`. csim's bus-cycle mode has to run bus cycles wherever the hardware does, or `resume6502()`'s 15-tick release can miss (fixed 2026-11-16 in atari800's `CPU_CSIM_Tick()`).
